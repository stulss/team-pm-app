# 보안 점검 결과

`DESIGN.md` §5 체크리스트를 항목별로 점검한 결과다. "근거"는 실제로 돌려 본 테스트나 배포본 확인이다. 마지막 점검: 2026-10-15 (서버 테스트 275개 · 실DB 스모크 159항목 · 브라우저 e2e 49단계 · 로컬에서 메일 켬/끔 모두 검증, 운영 반영은 푸시 후 재검증).

## 설계 체크리스트

| 항목 | 상태 | 근거 |
|---|:-:|---|
| 비밀번호 bcrypt(cost 12), 최소 8자 | ✅ | `utils/crypto.js`, 가입 검증 테스트. 응답에 해시가 노출되지 않음을 테스트 |
| 로그인 레이트리밋(IP+이메일) | ✅ | 배포본에서 같은 이메일 11번째 시도부터 429, 다른 이메일 영향 없음. 서로 다른 두 "인스턴스"가 Redis로 한도를 공유함을 확인 |
| Supabase anon/service_role 키를 클라이언트에 노출하지 않음 | ✅ | 클라이언트는 Supabase에 직접 접속하지 않고 번들에 키가 없음(`VITE_` 변수는 API 경로뿐) |
| `DATABASE_URL` 은 서버 환경변수로만 | ✅ | 서버 `config/env.js` 에서만 읽음. `.env*` 는 git 제외 |
| 전 테이블 RLS 활성화 | ✅ | 마이그레이션 001~005 마다 활성화, 실DB 스모크가 `relrowsecurity` 확인 |
| 모든 입력 zod 검증, SQL 파라미터 바인딩 | ✅ | 모든 라우트가 `validate()` 사용. SQL 은 값을 모두 `$n` 로 바인딩하고, 문자열을 이어 붙이는 곳은 컬럼 이름·`ORDER BY` 같은 **코드 상수**뿐(`PATCHABLE` 화이트리스트). 검색어의 `%`·`_` 는 이스케이프(스모크로 확인) |
| refresh 토큰 httpOnly + `SameSite=Strict` + 경로 한정 | ✅ | 배포본 응답 헤더 확인(`HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`). DB에는 SHA-256 해시만 저장, 회전, 재사용 감지 시 전체 세션 폐기(유예 10초, DB 시계 기준) |
| task/comment 접근 시 프로젝트 멤버십 검증 | ✅ | 권한 조합 테스트(Admin/소유 Manager/다른 Manager/Member/비멤버)와 e2e. 비멤버는 403. (설계의 "404 고려"는 UUID 추측이 어려워 403 유지) |
| 소켓 룸 입장도 멤버십 검증 | ✅ | `project:join` 이 매번 DB에서 활성 여부·멤버십 재확인(통합 테스트). 멤버 제거 시 방에서 내보내고, 비활성화·역할 변경 시 연결을 끊음 |
| 댓글 본문은 텍스트로 렌더링(XSS) | ✅ | e2e 에서 `<b>굵게</b>` 입력이 문자 그대로 보임을 확인 |
| 환경별 CORS 화이트리스트, helmet | ✅ | 동일 오리진이라 CORS 닫힘(테스트), helmet 헤더·CSP 확인 |

## 추가로 한 것

- **인증 필수 소켓**: 토큰이 없거나 잘못되었거나 비활성 사용자면 연결 거부(익명 연결 거부를 배포본에서 확인).
- **사용자 목록 노출 제한**: `GET /users` 는 Admin/Manager 만. 공개 가입이 열려 있어도 일반 계정이 팀원의 이름·이메일을 열람할 수 없다.
- **비밀번호 재설정**: 링크 토큰은 32바이트 난수이고 DB 에는 SHA-256 해시만 저장한다. 일회용(동시에 눌러도 한 번만 성공)·만료(1시간)이며 새 링크가 이전 링크를 무효화한다. 재설정 성공 시 모든 세션을 폐기한다. 요청은 가입 여부와 관계없이 같은 202 이고(계정 존재 비노출), 같은 사용자 60초 쿨다운 + IP+이메일 시간당 10회 제한으로 메일 폭탄을 막는다. 링크 주소는 `APP_URL` 설정으로만 만들어 Host 헤더 조작이 통하지 않는다. 메일 제공자 오류는 상태 코드만 로그에 남기고 사용자에게 사유를 알리지 않는다. 한계: 가입(409 `EMAIL_TAKEN`)과 이메일 초대(404)는 이메일 존재 여부를 알려 준다. **가입 시 이메일 인증은 하지 않으므로(2026-10-22 제거) 남의 이메일로도 가입할 수 있다** — 그 계정은 그 이메일 주인에게 재설정 메일이 가고, 비밀번호를 재설정해야 쓸 수 있다는 점이 유일한 방어다.
- **활동 기록**: 프로젝트 멤버(와 Admin)만 조회하며, 멤버에서 제거되면 즉시 볼 수 없다. 댓글 본문과 작업 설명의 내용은 기록하지 않는다(수정·삭제된 내용이 남지 않게). 이름·제목은 기록 시점 값을 복사해 두므로 이름이 바뀌거나 계정이 지워져도 기록이 유지되고, 180일이 지나면 정리한다. 기록 저장 실패는 본 요청을 실패시키지 않는다(드물게 기록이 빠질 수 있음).
- **히스토리 공유 링크**: 로그인 없이 읽는 공개 경로라 가장 보수적으로 만들었다. 토큰은 32바이트 난수이고 DB 에는 SHA-256 해시만 저장한다(원문은 만들 때 한 번만 보임, 추측·무차별 대입은 사실상 불가능). 만료 필수(1/7/30일)·즉시 폐기·프로젝트당 5개 제한, 없는/만료/폐기 토큰은 같은 404 로 구분되지 않는다. 공개 응답은 활동 기록만 담고(댓글 본문은 애초에 기록하지 않음) **멤버 정보와 공유 사실 자체는 제외**하며, 이메일·ID 는 나가지 않는다. `no-store`·`noindex`, 페이지 `referrer: no-referrer`, IP 분당 120회 제한. 링크 생성·폐기는 멤버가 보는 활동 기록에 남는다. 한계: 링크를 가진 사람이 다른 사람에게 전달하는 것은 막을 수 없고(만료·폐기로 대응), 공개 화면에는 작업 제목·담당자·행위자 이름이 보인다(만들기 전에 화면에서 안내). CSV 는 클라이언트가 만들며 UTF-8 BOM 과 수식 주입 방지(`=+-@` 로 시작하는 칸에 `'`)를 적용한다.
- **투표**: 프로젝트 멤버(와 Admin)만 읽고 만들고 투표할 수 있고, 마감·삭제는 만든 사람·소유자·Admin 만, 보관된 프로젝트는 읽기 전용이다. **익명 집계**: 응답에는 득표수와 본인 선택만 있고 누가 어디에 투표했는지는 없다(소유자·Admin 도 마찬가지). 단일 선택의 1인 1표는 투표 행을 `FOR UPDATE` 로 잠근 트랜잭션에서 "내 표 삭제 → 새 표 삽입"을 해 동시 요청에도 보장하고, 마감 확인도 같은 잠금 안에서 다시 해서 마감 후 표가 들어가지 않게 한다. `poll_votes` 의 복합 외래키가 다른 투표의 선택지에 대한 표를 DB 에서 막는다. 집계는 지금 멤버인 사용자의 표만 센다(제거되면 빠지고 다시 추가되면 되살아남). 투표는 프로젝트당 100개로 제한한다. 한계: DB 관리자는 `poll_votes` 에서 누가 투표했는지 볼 수 있다(화면·API 에서만 익명), 한 사용자가 여러 계정을 만들어 같은 프로젝트에 들어오면 여러 표를 던질 수 있다(공개 가입 + 멤버 초대 구조의 한계), 활동 기록·알림은 남기지 않는다.
- **모아보기**: `GET /feed` 는 본인 것만 돌려주며(사용자 ID 로 한정), 마감·멘션·활동은 모두 SQL 의 `project_members` 조인으로 **지금 멤버인 프로젝트**로 한정한다. 멤버에서 제거되면 즉시 사라지고, Admin 도 멤버가 아닌 프로젝트는 모아보기에 나오지 않는다(전체 열람은 프로젝트 화면·검색 권한 규칙을 따른다). 삭제된 댓글은 나오지 않고, 멘션 미리보기는 서버가 앞 80자로 자른 텍스트이며 화면에서 텍스트로만 그린다. 한계: 보관된 프로젝트의 활동과 멘션은 계속 나오고(마감 작업만 제외), 항목 수는 고정(마감 10·멘션 10·알림 5·활동 15)이라 더 오래된 것은 각 화면에서 봐야 한다.
- **통합검색**: 권한 필터를 **SQL 안에서**(`project_members` 조인, Admin 은 전체) 걸어, 접근할 수 없는 프로젝트의 행은 애초에 읽지 않는다(가져온 뒤 거르지 않는다). 멤버에서 제거되면 즉시 결과에서 사라진다. 검색어는 `ILIKE` 의 와일드카드(`%` `_` `\`)를 이스케이프해 글자 그대로 찾고, 값은 모두 바인딩 파라미터로 넘긴다(SQL 문자열에 끼워 넣지 않음). 삭제된 댓글은 검색하지 않는다. 검색어는 2~50자, 사용자당 분당 30회로 제한하고 로그에 남기지 않는다. 결과 snippet 은 서버가 만든 텍스트이고 화면에서도 텍스트(`<mark>`)로만 강조한다. 한계: 보관 프로젝트도 검색되고, 2글자 검색어는 인덱스 이점이 작아 데이터가 많아지면 느릴 수 있다. 활동 기록·알림은 검색하지 않는다.
- **채팅 멘션(M12b)**: 댓글 멘션과 같은 서버 검증(활성 프로젝트 멤버만, 본문에 `@이름` 필수, 최대 10명, 아니면 400 `INVALID_MENTION` 이고 메시지도 저장 안 됨), 본인 멘션은 알림 없음. 알림은 작업 없이 프로젝트에 연결되며(`task_id` NULL, `project_id`), DB 제약이 둘 다 없는 알림을 막는다. 메시지를 지워도 이미 간 알림은 회수하지 않는다.
- **채팅**: 프로젝트 멤버(와 Admin)만 읽고 쓸 수 있고, 멤버에서 제거되면 즉시 막힌다(REST 는 매 요청, 소켓 룸 입장은 입장 때마다 검증). 본문은 1~2000자 문자열로만 저장·렌더링한다(HTML 해석 없음, DB CHECK 제약도 건다). 보내기는 사용자당 분당 30건으로 제한한다(도배 방지). 저장 용량 보호를 위해 90일이 지난 메시지는 일일 cron 이, 프로젝트당 5000건을 넘는 오래된 메시지는 보낼 때마다 지운다. 삭제는 작성자·프로젝트 소유자·Admin 만, 보관된 프로젝트는 읽기 전용이다. 한계: 메시지 수정·파일 첨부·멘션·읽음 표시는 없고, 삭제는 실제 삭제라 되돌릴 수 없으며, 프로젝트 소유자와 Admin 은 멤버의 메시지를 지울 수 있다. 채팅 내용은 종단간 암호화가 아니므로 DB 에 평문으로 저장된다(Supabase 접근 권한자가 볼 수 있음).
- **멘션**: 멘션 대상은 자동완성에서 고른 **ID 를 명시적으로** 보내며 서버가 다시 검증한다(활성 프로젝트 멤버만, 최대 10명). 본문에 그 사람의 `@이름` 이 실제로 있어야 하므로 "보이지 않는 멘션"으로 알림만 보내는 스팸이 불가능하다. 본인 멘션은 알림이 가지 않고, 수정으로 같은 사람을 다시 알리지 않으며, 멘션과 댓글 알림이 겹치면 하나만 보낸다(알림 폭탄 방지). 멘션 강조는 텍스트로만 렌더링한다(HTML 해석 없음). 한계: 같은 이름의 멤버가 둘이면 본문 텍스트만으로는 구분이 안 되고(자동완성에는 이메일이 함께 보임), 멘션을 철회해도 이미 간 알림은 회수하지 않는다.
- **사용량 상한**: 공개 가입에서 무료 DB 용량을 지키기 위해 사용자당 프로젝트 20개, 프로젝트당 멤버 50명·작업 1000개(환경변수로 조정, 초과 시 409 `LIMIT_REACHED`). 동시 요청이면 한두 건 넘을 수 있는 소프트 상한이다.
- **가입 차단 스위치**: `ALLOW_REGISTRATION=false`. 첫 계정은 항상 허용, 이후 가입은 403 `REGISTRATION_CLOSED`.
- **DB TLS 서버 인증서 검증**: 내장한 Supabase Root 2021 CA(SHA-256 지문 고정 테스트, 유효기간 2031-04-26). 이전의 `sslmode=no-verify` 를 대체. 같은 CA 로는 풀러 2종이 검증을 통과하고 시스템 기본 CA 로는 실패함을 확인.
- **마감 Cron 인증**: `Authorization: Bearer CRON_SECRET` 을 상수 시간 비교, 미설정이면 503(비활성).
- **요청 크기 제한 100KB**, API 응답 `Cache-Control: no-store`, `x-powered-by` 제거.
- **로그에 비밀 미포함**: 구조화 로그에서 Authorization·쿠키·비밀번호·토큰을 redact. 운영 로그 200건에서 Bearer 토큰·refresh 쿠키·JWT 형태 문자열·테스트 비밀번호가 0건임을 확인.
- **의존성 점검**: `npm audit` 운영·개발 의존성 모두 취약점 0건.
- **계정 존재 여부 비노출**: 없는 이메일과 틀린 비밀번호가 같은 응답이고 응답 시간 차이도 없음(더미 해시 비교).
- **즉시 권한 반영**: 요청마다 사용자를 DB에서 다시 읽어 역할 변경·비활성화가 토큰 만료(15분)를 기다리지 않는다.
- **API 토큰(M32·M33)**: 값은 발급 응답에서 한 번만 보이고 DB 에는 SHA-256 해시만 둔다(로그·활동 기록·목록 응답에 값 없음). 토큰은 발급자 권한을 넘지 못하며 읽기 토큰은 GET 만 된다. 계정·세션·토큰 관리·알림·GitHub 연동·공유 링크·프로젝트 삭제·멤버 변경은 JWT 로그인으로만 가능하다. 폐기·만료·사용자 비활성화는 다음 요청부터 바로 적용된다(JWT 와 달리 15분 지연 없음). 토큰별 분당 120회 제한, 토큰으로 한 일은 활동 기록에 이름이 남는다. 한계: 쓰기 토큰이 유출되면 발급자 권한으로 작업·댓글이 바뀌므로 만료일과 읽기 전용을 권장한다.

## 검증 중 발견해서 고친 보안·정합성 문제

| 문제 | 어떻게 발견했나 |
|---|---|
| 서버가 소켓을 끊으면 클라이언트가 자동 재연결하지 않아 권한이 바뀐 사용자가 실시간 갱신을 못 받음 | 연결 끊김 보정 e2e |

| 웹소켓 임시 스파이크 페이지(익명 메시지 전송)가 공개 배포에 남을 뻔함 | 공개 전 점검 → 제거 |

## 알려진 한계 (수용하거나 후속 과제)

1. **Redis 구간 평문**: 무료 Redis 는 TLS 를 지원하지 않는다(`rediss://` 거부). 소켓 이벤트·레이트리밋 카운트가 평문으로 오간다. 이벤트에는 비밀번호·토큰을 싣지 않으며, 작업 제목 등은 포함된다. 민감한 내용을 다루면 TLS 가능한 Redis 로 교체한다.
2. **공개 가입(결정사항)**: 가입을 열어 두고 누구나 쓰게 한다. 가입자는 자신이 만들었거나 초대받은 프로젝트에만 접근하고 사용자 목록은 볼 수 없다. 대신 이메일로 초대하는 API 는 "그 이메일이 가입자인지"를 알려 주므로(없으면 404) 이메일 존재 여부가 노출된다. 가입·API 레이트리밋과 사용량 상한(프로젝트 20/멤버 50/작업 1000)으로 용량 악용을 줄이며, 악용 시 `ALLOW_REGISTRATION=false` 또는 Admin 의 계정 비활성화로 대응한다.
3. **환경 분리 없음**: Production·Preview·로컬이 같은 DB·Redis 를 쓴다. 실제 운영 시 개발용을 분리한다.
4. **레이트리밋 fail-open**: Redis 장애 시 레이트리밋이 풀린다(서비스 가용성 우선 결정).
5. **CSRF**: 상태 변경 API 는 `Authorization: Bearer`(메모리 보관) 로 인증하고 refresh 쿠키는 `SameSite=Strict` + 경로 한정이라 별도 CSRF 토큰은 두지 않았다.
6. **2단계 인증 없음**: 범위 밖. 가입 시 이메일 인증도 없다(2026-10-22 제거). 비밀번호 재설정은 메일 서비스(Brevo)를 설정해야 켜지고, 설정하지 않으면 비밀번호를 잊은 사용자를 구제할 수 없다.
7. **감사 로그 UI 없음**: 요청 로그(`x-request-id`)로 추적한다.
8. **Supabase CA 만료(2031-04-26)**: 교체 전까지 `DB_SSL_VERIFY=false` 비상 스위치가 있다.
